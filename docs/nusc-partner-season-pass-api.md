# NUSC partner season pass API

This API lets NUSC issue AHIBI tickets after NUSC verifies payment in NUSC's own Razorpay account. It never creates an AHIBI Razorpay order. It is server-to-server only.

## Identity and pass rules

- `general-season` issues ten `General Pass` tickets. NUSC supplies one `zone` (`G-1` through `G-5`); that same zone is applied to all ten fixtures.
- `premium-season` issues ten `Premium Pass` tickets and takes no zone.
- The NUSC `memberReference` must be a stable opaque member identifier, not an email address. AHIBI stores only a SHA-256 hash of it and does not create or link an AHIBI user account. A later account claim must use a separate verified ownership flow.
- AHIBI resolves the ten event Mongo IDs from its configured date slugs. Read them from the catalog endpoint; do not send event IDs, prices, or ticket counts in reservation requests.

## Authentication

Every request must use HTTPS and these headers:

```text
X-Ahibi-Key-Id: <environment-specific key id>
X-Ahibi-Timestamp: <Unix seconds>
X-Ahibi-Request-Id: <unique id for this HTTP attempt>
X-Ahibi-Signature: <lowercase hex HMAC-SHA256>
Content-Type: application/json
```

Calculate the signature over the exact raw body bytes:

```text
bodyHash = lowercase_hex(SHA256(rawBody))
message = timestamp + "\n" + requestId + "\n" + UPPERCASE_METHOD + "\n" + pathAndQuery + "\n" + bodyHash
signature = lowercase_hex(HMAC_SHA256(environmentSecret, message))
```

For an empty body, `rawBody` is zero bytes. `pathAndQuery` is the complete path beginning `/api/nusc-partner/v1`. Requests older than five minutes are rejected. A request ID can be accepted only once per key ID; give every retry a fresh request ID. Business retries remain idempotent through `partnerOrderId` and `paymentId`.

The API is disabled unless `NUSC_PARTNER_API_ENABLED=true` and the database/environment guard matches. Test uses `NUSC_PARTNER_TEST_KEY_ID` and `NUSC_PARTNER_TEST_SECRET` only with non-production `NUSC_HOME_MATCH_TEST_MODE=true` and Mongo database `ahibi-test`. Production uses `NUSC_PARTNER_LIVE_KEY_ID` and `NUSC_PARTNER_LIVE_SECRET` only with `NODE_ENV=production` and database `ahibi`. Never share these values in chat or logs.

## Endpoints

Base path: `/api/nusc-partner/v1`.

### Read current pass and event catalog

`GET /catalog/season-passes`

Returns current event IDs resolved from AHIBI's ten configured fixture slugs:

```json
{
  "success": true,
  "passes": [
    { "passId": "general-season", "ticketType": "General Pass", "generalZoneRequired": true, "zoneRule": "one selected zone is applied to all ten matches" },
    { "passId": "premium-season", "ticketType": "Premium Pass", "generalZoneRequired": false, "zoneRule": null }
  ],
  "matches": [
    { "matchIndex": 1, "matchDate": "2026-11-14", "opponent": "Gokulam Kerala FC", "eventId": "<AHIBI_EVENT_ID>", "eventSlug": "nusc-home-match-20261114" }
  ]
}
```

The response contains all ten matches; one is shown above as an example.

### Reserve a pass

`POST /season-pass/reservations`

```json
{
  "partnerOrderId": "nusc-order-<opaque-id>",
  "memberReference": "<opaque-nusc-member-id>",
  "passId": "general-season",
  "zone": "G-3"
}
```

Use `partnerOrderId` generated by NUSC before payment and reuse it for reservation retries. The request creates a 15-minute hold for one pass across all ten matches. A retry with the same order and same selection returns the original reservation; a changed member, pass, or zone conflicts.

On success (`201`, or `200` for an idempotent retry):

```json
{
  "success": true,
  "reservation": {
    "reservationId": "nsp_<40 lowercase hex characters>",
    "partnerOrderId": "nusc-order-<opaque-id>",
    "passId": "general-season",
    "status": "held",
    "expiresAt": "<ISO-8601 timestamp>",
    "zone": "G-3",
    "matches": [
      { "eventId": "<AHIBI_EVENT_ID>", "matchDate": "2026-11-14", "opponent": "Gokulam Kerala FC" }
    ]
  }
}
```

The returned `matches` array has all ten events. Sold-out or unavailable inventory returns `409` before NUSC should charge the member.

### Confirm NUSC payment and issue tickets

`POST /reservations/{reservationId}/confirm`

```json
{ "paymentId": "<NUSC_RAZORPAY_PAYMENT_ID>" }
```

Call only after NUSC has verified capture server-side. AHIBI trusts this assertion only after validating the signed partner request. It creates exactly ten AHIBI bookings at zero AHIBI charge. `201` means newly issued; a retry with the same reservation and payment ID returns the same ten tickets with `200`. Reusing a payment ID on a different reservation conflicts. An expired hold returns `409 HOLD_EXPIRED`; NUSC should follow its own refund/reconciliation process.

```json
{
  "success": true,
  "issuance": {
    "reservationId": "nsp_<40 lowercase hex characters>",
    "partnerOrderId": "nusc-order-<opaque-id>",
    "paymentId": "<NUSC_RAZORPAY_PAYMENT_ID>",
    "status": "issued"
  },
  "tickets": [
    {
      "match": { "eventId": "<AHIBI_EVENT_ID>", "matchDate": "2026-11-14", "opponent": "Gokulam Kerala FC" },
      "ticketId": "<AHIBI_BOOKING_ID>",
      "status": "confirmed",
      "ticketType": "General Pass",
      "zone": "G-3",
      "ticketAccessPath": "/api/nusc-partner/v1/reservations/<reservation-id>/tickets/<booking-id>"
    }
  ]
}
```

The `tickets` array contains ten items. It contains no QR payload. The signed ticket endpoint below supplies the QR payload to NUSC's backend when needed; keep it out of application logs and public events.

### Release an unpaid hold

`POST /reservations/{reservationId}/release`

Call when payment fails or NUSC checkout expires. A held reservation is released; issuing or issued reservations cannot be released through this endpoint.

### Recover status after a timeout

`GET /reservations/{reservationId}`

Returns reservation status and, if issued, the same ten ticket records. NUSC may safely retry confirm with the same payment ID if status is still `held` or `issuing` and the hold has not expired.

### Retrieve one ticket for the NUSC dashboard

`GET /reservations/{reservationId}/tickets/{bookingId}`

Returns the booking ID, event ID, match date/name, ticket type, zone, status, and `qrPayload`. This endpoint is protected by the same service signature; do not call it from a browser with partner credentials.

### Download one issued ticket as an AHIBI PDF

`GET /reservations/{reservationId}/tickets/{bookingId}/pdf`

Send the same signed service-to-service headers used for every other endpoint. The HMAC path includes the complete path from `/api/nusc-partner/v1`, and the body is empty for this GET. Keep the partner key ID and secret on NUSC's server; never make this request from a browser.

AHIBI returns the existing AHIBI ticket PDF format as a binary response. The booking must be active and its ID must belong to the supplied reservation's issued `bookingIds` list. A missing booking and a booking belonging to another reservation both return `404 TICKET_NOT_FOUND`.

Success response headers:

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="ahibi-ticket-<24-hex-booking-id>.pdf"
Cache-Control: private, no-store, max-age=0
X-Content-Type-Options: nosniff
```

The response body is the PDF file. It is generated for this authenticated request; AHIBI does not return a public or permanent ticket URL. Other errors include `401 INVALID_PARTNER_SIGNATURE`, `409 TICKET_NOT_ACTIVE`, and `500 TICKET_PDF_FAILED`.

For NUSC's accountless members, use the signed POST form to render attendee details into the ticket:

`POST /reservations/{reservationId}/tickets/{bookingId}/pdf`

```json
{
  "attendee": {
    "name": "Member name",
    "email": "member@example.com",
    "phone": "+91 98765 43210"
  }
}
```

The signature must use method `POST`, the complete path and query beginning `/api/nusc-partner/v1`, and the exact UTF-8 JSON bytes sent as the request body. Do not reformat or reserialize the body after signing. Use a new timestamp and unique request ID for every attempt; the existing HMAC formula and headers apply. The request requires all three fields: trimmed name (1–100 characters), valid email (up to 254 characters), and phone (up to 40 characters). Unknown fields are rejected with `400 INVALID_ATTENDEE`.

The supplied attendee fields are used only while rendering this response. AHIBI does not save them to the booking, create or link an AHIBI account, or include them in request logs. The PDF response and its headers are the same as GET. The existing GET method remains available and renders stored booking details when present, with placeholders otherwise.

## Status and recovery behavior

- `held`: inventory reserved until `expiresAt`.
- `issuing`: NUSC payment ID has been accepted; retry confirm with the same payment ID or query status to complete/recover partial ticket writes. The original hold expiry no longer blocks an issuance already in progress.
- `issued`: the same ten booking IDs are returned on every confirm/status retry.
- `released` / `expired`: no tickets were issued. A newly paid order must be refunded or reconciled by NUSC rather than confirmed against this reservation.
- No outbound webhook is used in v1. Confirm response plus signed status lookup is the recovery path.

## Test environment

For local acceptance testing, keep the protected API running in Terminal 1:

```powershell
cd D:\projects\AHIBI\server
$env:PORT = '5001'
npm run dev:nusc-test
```

In Terminal 2, run the test suite against loopback:

```powershell
cd D:\projects\AHIBI\server
$env:NUSC_HOME_MATCH_TEST_MODE = 'true'
$env:NUSC_PARTNER_TEST_BASE_URL = 'http://127.0.0.1:5001/api/nusc-partner/v1'
npm run test:nusc-partner
Remove-Item Env:NUSC_HOME_MATCH_TEST_MODE, Env:NUSC_PARTNER_TEST_BASE_URL
```

The protected `npm run dev:nusc-test` launcher redirects the configured Mongo URI to `ahibi-test`, requires a Razorpay test-key prefix, enables the test gates, and refuses `NODE_ENV=production`. Configure `NUSC_PARTNER_API_ENABLED=true` and the test key pair privately in the AHIBI test environment before starting. The acceptance suite simulates a captured NUSC payment ID without contacting Razorpay; it writes temporary records and inventory counters in `ahibi-test`, then removes its test tickets and holds. Let it finish before stopping the process. Do not use production credentials or a production database.
